## 1. 計画の目的と前提

最初に1社・1チームで動くMVPを開発し、自動配置の正しさ・計算時間・管理者の修正負担・スタッフの使いやすさを検証する。検証結果を踏まえ、複数企業向けSaaSとして現在の初期版要件を備えたv1.0へ進める。

本書は開発順序と範囲の提案であり、これまでの確定要件を取り消すものではない。「MVP」と「本開発後のv1.0」を区別し、設計書本文・第20・22章のQ73〜Q131を含む初期版要件はv1.0で満たす方針とする。将来AI候補や、現時点で対象外の機能は別の追加開発とする。

| 項目 | 計画上の仮定 |
| --- | --- |
| 初期利用 | 1社・1チーム。対象人数は実際の試験チームに合わせる |
| 最初の性能検証 | 101人・1か月から開始し、早期に500人ケースも計測 |
| 期間・時間粒度 | 暦月1か月。業務30分／60分、出退勤・休憩30分、準備・移動・最低継続は分単位 |
| 開発体制 | Web／API担当2人＋数理最適化担当1人が主に専任 |
| 業務側 | プロダクト責任者・試験チーム管理者が週次で判断・評価。QAは兼務または部分参加 |
| MVP期間 | 12〜16週間程度。標準案は16週間 |
| 本開発期間 | MVP判定後に追加16〜24週間程度 |
| 全体期間 | 約7〜10か月程度。実データ・体制・検証結果により再見積もり |
| 開始日・予算 | 未指定。相対週で計画し、採用技術・体制決定後に費用を算出 |

期間は上記体制を仮定した計画値であり、納期の保証ではない。1人での開発、最適化担当の兼務、データ整備の遅れがある場合は延長する。工程表の担当分担は実際の開発チーム向けであり、現時点で開発を開始したことを意味しない。

| スタッフ画面 | 自分の公開版、希望登録、休暇申請、お知らせ | スマートフォンでの操作性・表示を改善 |
| 出力 | 確定シフトのCSV | Excelを追加。CSVとも勤務日・出退勤・休憩のみ。業務配置出力は対象外 |
| AI-01 説明 | 今回対象外（ADR 0097）。計算状態・不足・違反の表示は維持 | 構造化した根拠・AI要約・定型切替と評価・版管理 |
| AI-02 比較 | 比較用の評価指標と計算条件を保持。比較機能は本開発へ | 元案と代替案の再計算・比較・AI要約。代替は1案（Q105） |
| 運用 | 運営体制・監視・引渡し・運用手順は今回対象外（ADR 0097）。技術的な障害復旧は維持 | バックアップ運用、RPO／RTO判定、複数企業運用、監視・障害対応手順 |

MVPでは対応する設定やファイル形式を絞る。対象チームの勤務条件を無視したり、違反を許容して計算を成立させたりはしない。対象チームに必要な役割評価や休憩ルールが標準構成と異なる場合は、当該条件をMVPへ組み込むか、試験対象を合意して調整する。

MVPで人数算出を行わない間は、現在の運用で算出・確認した需要値を直接入力・CSVで渡す。電話・事務・チャットは業務として配置できるが、各チャネルの必要人数算出エンジンは本開発で接続する。

設計書第15章の「初期版AI」はv1.0の範囲である。ADR 0097によりAI-01・AI-02とも今回の完成条件から外し、後続工程で検証する。既存の計算状態・不足・違反の表示と配置検証は維持する。

## 5. A1：最適化の試作と判断

1. 小人数・数日で確認できるモデルを作り、勤務選択・分単位区間・30分時刻・休憩・能力換算を検証する。
2. 1か月の勤務上限・下限、週開始曜日、連続勤務、前月境界を追加する。
3. スキル、役割、固定予定、業務継続時間、準備・移動を追加する。
4. 理由付き固定例外と、公開後の出退勤・休憩固定を検証する。
5. 不足・希望・余剰の評価を接続し、設定と結果を再現可能にする。
6. 101人・試験チーム人数・500人の各ケースを計測する。
7. 本体アプリとの入出力契約と、最適化方式を決定する。

| 成果物 | 内容 |
| --- | --- |
| 計算試作 | 入力ファイルからシフト・配置・不足・計算状態を出力 |
| 独立した条件チェッカー | ソルバーが返した案を通常の業務ロジックで再検証 |
| 試験データ | 既知の実行可能ケース、矛盾ケース、人数不足ケース、休暇・固定ケース |
| 計測結果 | 変数・条件数、モデル準備時間、探索時間、メモリ、不足・希望・余剰 |
| モデル選定メモ | 全体同時計算／段階計算の採用理由、残る性能課題 |

この段階の500人計測は性能リスクの把握であり、500人対応の達成宣言ではない。画面の表示速度と計算の探索時間は分けて記録する。

問題がある場合は、不要な候補変数の削減、既存案の利用、計算の段階化などを検討する。段階化で配置可能性を失う場合は、後段の不足・矛盾を前段へ戻して修正する。計算速度のために必須条件を削らない。

実装単位ごとにAPIと画面をつなぎ、登録から公開まで小さな経路を完成させる。独立したUI作業とAPI作業は並行できるが、計算モデル・評価指標の変更は共有の入出力契約へ反映する。

## 7. A3：試験運用の進め方

- 試験チームの現行運用と同じ需要・契約・希望データを使い、1か月分を作成する。
- 初期は現行運用と並行して結果を比較し、管理者が確認した案を採用する。
- 不足・希望不一致・手動修正・固定・例外の件数と作業時間を記録する。
- 公開、スタッフ確認、休暇申請、固定解除、承認、欠勤登録、再配置、再公開を試す。
- 説明の数値・根拠を確認し、AIの訂正理由を記録する。
- 毎週、管理者と開発担当で問題を分類し、仕様・計算・データ・画面のどこに原因があるか整理する。
- 他企業のデータを扱う試験は仮想テナントで実施し、実導入が1社でも分離の検証を省略しない。

実データ利用の範囲と公開対象は試験企業と合意する。実データが準備できない場合は匿名化・合成データで開発を進められるが、現場での有用性の判定は実データ・管理者評価を待つ。

## 8. MVPから本開発へ進む判定基準案

以下は計画上の受入基準案。数値のある目標はA0で管理者と確定する。

| 項目 | 判定基準案 | 判定方法 |
| --- | --- | --- |
| 必須条件 | 未承認の勤務不可配置、勤務・契約違反などが0件 | 独立した条件チェッカーと境界・矛盾ケース |
| 手動例外 | 理由付き固定例外の対象だけを維持し、例外が他配置へ広がらない | 固定・理由・スタッフ・日付の組み合わせを検証 |
| 計算状態 | 実行可能、未最適、未発見、実行不可能、失敗を正しく区別 | 既知ケースと時間制限ケース |
| 計算時間 | 合意した試験規模で開始操作から検証済み案表示まで総時間300秒程度を目標とし、有効案を得る | 複数の通常・繁忙・欠勤ケースを同じ環境で計測 |
| 配置品質 | 同じ入力・評価方式の現行案に対し、優先順位に沿った不足評価が悪化しないことを目標 | 役割先行なら役割不足→一般不足、同段階なら等重みの不足合計を比較。各不足も別記 |
| 希望充足 | 充足優先なら先行不足を維持して希望改善、希望優先なら希望を先に評価。現行案と同じ順序で比較 | 同じ評価順序・希望採点・分母で比較 |
| 業務効果 | 月間作成・確認・修正の合計時間を30%以上短縮する目標案 | 管理者の作業時間を記録。閾値はA0で合意 |
| 一連の操作 | 登録→計算→確認→公開→休暇→再配置を完了できる | 管理者・スタッフによる操作確認 |
| AI説明 | 表示した数値が集計と一致し、未確認の原因・改善量を断定しない | 代表ケースの評価、失敗時の定型表示確認 |
| 権限・履歴 | 他企業・担当外・他人のデータを参照できず、公開版と変更者を追跡できる | 権限試験・履歴確認 |
| 運用 | バックアップから復旧でき、ジョブ失敗が確認・再実行できる | 復旧・障害時操作を実施 |

300秒程度は通常計算の開始操作から検証済み案表示までの総時間目標（Q103）。待機・入力取得・準備・全探索段階・検証・集計・表示を含め、AI生成は除く。探索上限は総時間の残り予算から設定し、探索だけに300秒を与えない。同一チームの通常計算は1件まで（Q104）。A1で30分／60分配置と分単位処理を含む各段階を実測し、時間予算・達成条件をA4／B4で見直す。

最適性の証明はMVPの必須合格条件としない。性能・品質の目標が未達であれば、そのまま本開発を拡大せず、モデル改善・データ改善・試験条件の見直しを行う。運用上受け入れられる限定を置いて進む場合は、対応人数・機能・計算条件を明示して計画を更新する。

## 9. 本開発の工程案

本開発では、現在の初期版要件を満たすv1.0を完成させる。以下はMVP判定後の相対期間。

| 工程 | 期間目安 | 主な内容 | 完了判断 |
| --- | --- | --- | --- |
| B1：設定・運用基盤の拡張 | 4〜6週間 | 企業／雇用区分／個人の設定管理、複数チーム、利用者管理、Excel・CSV、履歴 | 設定の再現性と複数企業・チームの権限分離を確認 |
| B2：需要算出・評価方式の拡張 | 4〜6週間 | 電話・事務・チャットの人数算出、直接入力優先、希望優先・役割不足方式、性能改善 | 業務実績・既存算出との比較、全選択方式の条件検証 |
| B3：AI比較・操作性の改善 | 4〜6週間 | AI-02、差分・根拠表示、公開後の比較制限、管理者／スタッフ画面改善 | 元案＋代替案の指標一致、出退勤・休憩維持、管理者採用操作 |
| B4：500人・複数企業の検証と導入 | 4〜6週間 | 上限規模、同時ジョブ、負荷、復旧、回帰試験、追加チーム導入 | 全初期版の受入条件と運用条件を満たしv1.0としてリリース |

B1とB2の独立作業は並行できる。B3は比較可能な評価指標と条件管理の完成が必要。B4へ入る前にも500人計測を繰り返し、終盤に初めて性能問題が判明する進め方を避ける。

業務量からの必要人数算出は、電話の応答水準やチャットの同時処理に関する前提を確定してから実装する。待ち行列や処理能力の方式を未検証のまま採用せず、試験チームの需要・実績に照らして妥当性を評価する。

「500人を5分程度」は本開発の性能目標として検証する。台数・同時ジョブ数・入力条件を明示した測定結果を用意し、保証する範囲はリリース判定時に決める。

## 10. 本開発へ引き継ぐ設計

| 引き継ぐもの | MVPから持たせる理由 |
| --- | --- |
| 企業・チーム・本人のIDと権限 | 後からデータ分離を作り直す範囲を減らす |
| バージョン付き設定・計算入力 | 同じ条件で再現・比較できるようにする |
| ソルバーと通常の検証処理の分離 | 計算方式を変えても勤務条件の検証を維持する |
| シフトの下書き・公開版・固定・例外 | 公開後の運用を本開発で作り直さずに拡張する |
| 30分／60分の担当業務と分単位の状態区間 | 30分時刻・休憩・準備・能力換算の意味を一貫させる |
| 非同期ジョブと結果状態 | 計算の長時間化・複数企業利用へ対応しやすくする |
| 構造化した評価指標・根拠 | AI説明・AI比較を同じ事実から生成する |
| CSV列定義と入力検証 | Excelなどの入力形式追加でもモデルの入力を統一する |
| 運用データ・評価記録 | 本開発の優先順位と効果を根拠で決める |

一方、試作用のデータ生成・計測スクリプトやブラウザ保存は本番の業務保存に転用しない。汎用設定画面を後回しにしても、ルールをコードへ散在させず、設定データと検証としてまとめる。

## 15. モックから実装へ移す方針

旧参照モックは公開対象外とし、製品画面で画面と運用を確認する。モックのサンプル値・ブラウザ保存・擬似計算は本番データ処理ではない。
