# ADR 0018：本人申請と欠勤事実を取消確定から分ける

2026-10-11。WP-08。製品仕様はQ31／Q69／Q84／Q93〜Q97／Q109／Q121／Q128〜Q131を適用する。全日・半日のみ、日本時間、理由を記録する。固定解除・最低勤務量・公開済み休憩の検証前に勤務を取り消さない。

## 今回の判断と実装

本人の休暇申請・欠勤申請を`PENDING`、管理者の欠勤事実直接登録を`REPORTED`として保存する。事実は下限矛盾がある場合も記録できるが、取消確定を意味しない。管理者の理由付き却下は申請を`REJECTED`へ進める。事実記録そのものを却下・削除しない。受付・却下で公開版・配置・休憩・計算条件を変更しない。

`leave_record`は当初の公開版・スタッフ・日付・全日／午前／午後・理由・適用カレンダー版・対象区間・記録者を不変保存する。`leave_head`で申請ごとの状態・版、`leave_rejection`で却下者・理由・期待版を保存する。受理時の内容と現在状態は別で、同じ操作IDの再送は当初の受理結果を返す。画面はその後に現在状態を読み直す。

受付・却下は勤務条件に影響しないため企業の計算入力版を増やさず、申請版で競合を管理する。これにより申請理由の受付だけで計算や公開証明を古くしない。今後の承認・取消確定では入力版・公開版との原子更新を別途実装する。この区別を省き、受付をそのまま`staff_month`の勤務不可や公開取消へ変換する案は採用しない。

APIの権限確認に加え、D1 triggerで現在の利用権・初回変更完了・本人／担当管理者・所属・現在公開版・適用カレンダー版を再確認する。半日の区間を企業共通の区切りから求め、残る勤務がない受付を拒否する。休憩と既存取消の重複部分を勤務として数えない。SQLでも区間・実勤務分を検査する。将来日の「欠勤事実」は拒否する。本人の申請では管理者による他人のなりすましを認めず、欠勤直接登録を別の入口として使う。

同じスタッフ・日付・勤務範囲に残る未処理申請の重複を防ぐ。重ならない午前・午後は別々に受け付けられる。申請と事実記録は異なる目的なので両方を保持できる。同種の重複事実は拒否する。却下済み申請は履歴を残して再申請を受け付ける。

受付／却下・状態・本人の通知・監査をD1 batchでまとめる。0行更新の成功を確定証跡に使わず、期待版に一致しない場合はSQLでABORTする。[D1のbatch契約](https://developers.cloudflare.com/d1/worker-api/d1-database/)に加え、実Workerdで監査失敗時のロールバックを試験する。理由を外部のメール・キュー・AIへ送らない。

一覧と通知は50件のkeysetページで取得し、同時刻のIDを第2キーにする。スタッフは本人だけ、管理者は担当チームだけを参照する。既読は本人宛てだけ、再送で通知を増やさない。企業／チーム／本人の境界を読み取り前後に確認する。

ローカル専用の架空fixtureは、管理者に加え架空スタッフの初期資格情報を保護したレスポンスで返す。CLIはignoredの0600ファイルへ保存する。製品・PoC入口には組み込まず、終了時に両アカウントを無効化する。秘密値を証跡・コミットへ含めない。

## 未検証・後続

今回の受付・却下を、承認・取消確定の完成とは扱わない。固定の明示解除、現在条件と公開配置を使う取消仮検証、自動／固定休憩、月下限、予定参加解除、取消後の希望、公開版・不足・通知・境界履歴の原子的な即時同期、別操作での業務再配置公開を継続する。実Cloudflareの累積migration／配備、大規模・障害復旧・現場受入も別途必要。
