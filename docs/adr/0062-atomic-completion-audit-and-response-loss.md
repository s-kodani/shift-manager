# ADR 0062: 計算完了の監査を原子的に保証し、応答消失を確定状態で照合する

日付2026-10-13。WP-04／R-02／TS-API・REC。製品要件・最適化設定・最大3試行を変更しない。

## 問題と判断

完了batchの監査INSERTが0行で成功すると、計算結果だけがSUCCEEDED／NO_SOLUTIONへ採用される。`INSERT OR IGNORE`や`RAISE(IGNORE)`の0行はSQL例外ではなく、D1 batch自体の成功だけでは履歴の存在を保証しない。

結果の条件付き採用、canonical audit INSERT、採用結果に対応する監査の存在検査を同じD1 batchへ入れる。企業／job／attempt／result_keyが一致した採用に対し、auditの企業／ID／actor／kind／revision／確定時刻を照合する。欠落・別内容なら`abs(-9223372036854775808)`によるSQLite整数overflowを発生させ、全batchをrollbackする。旧attempt／別結果に負けた更新0行は通常のfalseのままである。スキーマ・監査の不変性を変更しない。

成功確定後に応答だけが失われる場合は、実行catchで同じ企業／チーム／jobのD1状態を読み直す。不変の終端状態ならDONEとし、重複Queue配送で再計算・重複監査を行わない。読取も失敗した場合はthrowし、既存DO fenceの照合へ戻す。停止未確認はこの照合より先にthrowするため、D1終端だけを物理停止の証拠にしない。R2書込後の応答消失で生じる未参照objectは自動採用せず、次attemptの新しい参照を使う。

## 代替と適用範囲

batch後に監査を読み、欠けたら補う方式では、監査なしの成功確定が外部から参照される期間を作る。監査INSERTのchangesだけを確認しても、既に確定したD1更新をrollbackできない。専用テーブル・移行を追加する方式より、現在の結果と監査を同一transaction内で照合する方が影響を限定できる。

応答消失時に無条件RETRYを返す方式は確定状態と配送指示を食い違わせる。終端状態の再読込も不可なら成功を推測しない。自動GC・孤立R2 objectの削除・復旧一般の完了を本変更へ含めない。

実施結果（過去の私有資料・公開対象外）で制御障害と実D1／R2・Docker独立checkの証跡を区別する。Cloudflareはローカル通過後の最終一括、定期backupは保留、保管30日を維持する。
