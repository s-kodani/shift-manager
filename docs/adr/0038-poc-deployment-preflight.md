# ADR 0038: PoC配備前の状態確認を必須にする

2026-10-12。状態: 実装・限定検証。製品仕様、通常のジョブ受付、バックアップの有効化保留は変更しない。実施記録（過去の私有資料・公開対象外）。

## 判断と理由

前回、D1照会の認証失敗を検査する前に配備を進めた。手動の確認だけに依存せず、`npm run deploy:poc`を確認・ビルド・再確認・配備の順で実行する。確認失敗、応答不明、記録失敗、ビルド失敗なら配備へ進まない。自動再試行や確認を飛ばすオプションは設けない。

専用PoCのBearer保護されたPOST `/__poc/deploy-preflight`で、通常ジョブQUEUED／RUNNING／CANCELLINGと再検証PENDING／RUNNINGをD1から取得する。稼働0なら、専用syntheticと登録された全チームのDOを4件ずつ照会する。RPC・計算フェンス・チェックフェンス・実プロセスのいずれかが残れば拒否する。その後、D1の件数とチーム一覧を再取得し、稼働0と一覧一致を検査する。1024チームを超える場合は部分的な確認で許可せず止める。

状態照会は業務データやジョブを変更せず、Containerプロセスを起動・終了しない。未初期化DOでは既存コンストラクターによる内部テーブル初期化が起こり得る。応答・証跡にはチーム／企業ID、bootId、秘密値を含めず、件数と判定だけを残す。HTTP成功、16KiB以下、厳密な応答形、30秒以内の確認時刻をクライアント側でも検査する。

## 採用範囲と限界

既存の非公開PoC URLと`infra/.dev.vars`のPOC_TOKENを使う。ローカル・本番では確認入口を拒否する。通常のdry-run、運営者Worker、バックアップWorkerのコマンドは変更しない。初回の入口導入のみ、従来のD1・synthetic状態確認を成功検査した上で直接配備する。この例外は実施記録に残す。新環境の導入時も、入口未配備の404を稼働0と解釈しない。

これは保守モードや新規受付を止める原子ロックではない。最終確認後に新規ジョブが入る競合、確認済みDOが後から起動する競合を完全には防げない。保守制御・反復障害受入はWP-10の残作業とする。稼働中状態を自動削除して配備を通す代替案は採用しない。通常ジョブの150秒期限・180秒lease、最大1Container、勤務条件・公開条件を維持する。

参照: [Workers best practices](https://developers.cloudflare.com/workers/best-practices/workers-best-practices/)。実コードのD1 batchとDO RPCは現行型定義とも照合し、依存版変更とは分離した。
