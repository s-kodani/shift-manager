# ADR 0122: スタッフ行の操作メニューと非アクティブ化・削除

日付: 2026-10-16。ユーザー依頼と追加確認への回答に基づく。

## 決定

スタッフ一覧の各行に三点リーダーの操作ボタンを表示する。企業管理者向けの管理者付与・解除をメニューへ移し、企業管理者と担当チーム管理者が非アクティブ化・再有効化・削除を選べるようにする。状態変更は氏名と影響を示した確認画面を経て実行する。キーボードで開閉・項目移動・選択でき、横スクロールする表の外側へメニューを表示する。

- 非アクティブ化: ログイン・既存セッション・未公開月の新規計算対象から外す。一覧に状態を残し、再有効化で既存のパスワード・初回変更必須状態・契約・条件・権限を引き継ぐ。
- 削除: ログインと新規計算対象から外し、スタッフ一覧から除外する。通常の再有効化はできない。勤務・公開・申請・監査履歴を壊さない論理削除とし、本人ID、企業内スタッフ番号、メールは再利用しない。CSVによる削除済み番号の更新も拒否する。
- 公開済みの勤務: 両操作で変更しない。その月の業務再配置では公開版に存在するスタッフを引き継ぎ、出退勤・休憩と既存の予定参加を維持する。公開済み月に存在しない非アクティブ／削除済みスタッフは追加しない。
- 未公開月の研修・会議: 新規計算時の有効な参加者から対象者を外す。元の計画版は保持し、再有効化で元の登録を参照する。未知のスタッフIDの入力拒否は維持する。
- 新規計算対象が0名の場合は、その理由とスタッフ登録・再有効化の案内を返す。

企業管理者アカウント、自分自身、他企業・他チームにも所属する共有アカウントは停止・削除できない。アカウントの停止が全所属へ影響するため、担当チームの操作で他の権限を失わせない。

## 実装と整合性

`0034_staff_lifecycle.sql`でスタッフの状態と不変の操作台帳を追加する。`POST /api/companies/:company/teams/:team/staff/:staff/status`は`operationId`・`expectedRevision`・`status`を受け取り、対象チームの管理権限をAPIとトランザクション内で検査する。状態・認証の停止／再開・セッション失効・入力版・監査を同一バッチで保存し、更新行が0件の場合を含め最終値を検査する。同じ操作IDの再送は再適用せず、異なる内容や版競合を拒否する。

公開時の人数チェックは計算対象と同じ集合（アクティブ＋当月公開版の既存スタッフ）を使う。取消時は親公開版の人数を維持する。公開後の勤務条件や最低勤務量の検証を緩めない。

## 代替案・検証範囲

物理削除は公開勤務・個人条件・申請の外部キーと監査の保持に矛盾するため採用しない。単なる画面非表示では、既存セッションや古い計算結果を防げないため、サーバーの状態・版も更新する。

統合テストは実ローカルD1/R2・Better Authを使用する。公開・再配置の試験は制御したソルバー／チェッカー応答による状態整合性の検証で、ネイティブ最適化の追加性能試験とは区別する。画面と実施結果は検証記録（過去の私有資料・公開対象外）へ記載し、Cloudflareへの反映は別途行う。
