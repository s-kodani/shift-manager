# ADR 0024: 本人提出期限は前月の指定日・月末補正とする

2026-10-11。状態：ユーザーが製品仕様を確定。日時計算・本人提出API・受付再開と画面を実装。受入範囲と未検証事項は後続の実施記録に分ける。

## 確定した回答

ユーザー回答：**「前月の締切日とし、存在しない日は月末に補正する」**。

追加のユーザー回答：**「勤務不可・希望とも同じ締切を適用する」**。本人の勤務不可日時の登録・変更にも、希望と同じ前月締切・管理者の受付再開を適用する。勤務不可の必須条件扱いは維持する。

Q88の企業共通日を対象シフト月の前月へ適用する。10月・締切20日は9月20日23:59日本時間。3月・31日なら平年2月28日、閏年2月29日。1月なら前年12月。企業設定の31を28へ書き換えず、対象月ごとに補正する。Q108の日本時間を維持する。

表示した23:59の分まで受付可能とし、翌日00:00を排他的な境界にする。サーバー時刻が境界未満なら期限前、境界と一致すれば締切後。ブラウザのローカルtimezoneや端末時計を許可判定の根拠にしない。

Q89の締切後の受付再開、Q99の企業共通設定は企業管理者のみ、本人の強さ指定なし、希望項目ごとの同じ強さ、未提出は希望なしという既定を維持する。ソルバーは受理済みの希望だけを採点し、締切を独自判断して変更しない。

## 実装・試験と残る作業

`submission-deadline.ts`で、既存の月契約と日1〜31を検証してUTC演算から日本時間の境界を返す。通常日、月末・閏年・年越し、23:59分内／翌日境界、不正値の4試験と型チェックが合格した。日時計算は受付を許可するAPIではない。

日時計算の先行段階では、本人登録・同ID再送、勤務不可／希望の版、管理者の担当範囲内の受付再開、保存時点の原子的な期限・版・権限検査、入力スナップショット・公開済み条件への影響、PC／モバイルは未実装または未検証だった。後続の実装・限定検証は以下と実施記録で区別する。日時関数の合格をTS-NEW-07全体の合格と扱わない。実施結果は進捗（過去の私有資料・公開対象外）へ記録する。

## 本人提出・再開の実装判断

本人エンドポイントは認証済みユーザーからスタッフを企業・チーム内で解決する。受信したスタッフID・例外・固定・採点の強さは受け付けない。企業管理者と担当チーム管理者は、対象チーム・月の追加受付を現在から指定した終了日時まで開き、追加受付だけを終了できる。通常の締切より前の本人入力は追加受付終了後も許可される。これはQ89の受付再開を実装する範囲であり、企業共通日をチームごとに変更する機能ではない。

受付期間は入力条件ではないため専用の版と不変監査を持つ。再開だけで計算の入力版を更新しない。本人保存は既存の `staff_month` の不変版・企業入力版・固定元・監査へ原子的に反映し、公開済み月の再検証の既存トリガーへ接続する。受付期間と設定版は保存時点のD1内でも検査する。翌日00:00境界は排他的。終了後の同じ操作ID・同じ内容の再送は既存保存の確認だけを返し、新しい内容は拒否する。

本人提出の実施記録（過去の私有資料・公開対象外）でローカル試験・画面確認・Cloudflare実環境検証を分ける。日時の単体4件だけでTS-NEW-07全体を合格としない。
