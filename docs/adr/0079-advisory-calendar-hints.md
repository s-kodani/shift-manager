# ADR 0079: 週・月上限を満たす補助カレンダーのヒント候補

2026-10-14。状態：技術候補・通常未採用。R-01／TS-PERF-02・04。製品の勤務量・全候補・本体制約・目的順序を変えない。

5業務／10パターンの架空101人で、通常初期ヒントの最長勤務選択が週750分・月3300分を超え、2つの限定seedがINFEASIBLE、本探索UNKNOWNとなった。独立checkerで同じ最長勤務の上限違反を確認した。入力自体の解なしを意味しない。

`mvp-joint-calendar-roster-v1`に限定し、個人の候補から補助CPで月最低／上限・日数／休日・週上限・連勤・既知履歴を満たすカレンダーを作る。勤務不可・固定・予定・日上限等は本体と同じ候補生成の適格性を使う。役割・業務の本体モデルを置き換えず、この案を解や全目的の証明として返さない。補助目的は需要がある処理分の量だけのヒューリスティックで、製品の段階目的ではない。

呼出し内6秒・個別CP最大0.25秒・worker1／seed0。同じ日別の線形係数・上限／下限・履歴だけが同じ場合に、同じ呼出し内で選択indexをreuseする。未知の前月履歴を0とみなさず補助案を作らない。枠不足・未取得なら元のヒントへ戻す。covered-offの月下限検査は補助案の実際の勤務量・日数を使う。元の本体モデルの全候補を維持し、hint以外の初回full protoは両優先順位で一致を検査する。

101人ではFEASIBLE／別check VERIFIEDを得た。役割先行の評価は参照案より良く、一般不足は増えた。辞書式改善を全不足・希望品質の改善へ読み替えない。500人は6 GiBに達しOOM kill／HTTP500となったため、規模受入・通常採用は保留する。実施記録（過去の私有資料・公開対象外）に失敗・資源・検査範囲を保持する。

次はOOM時の工程を切り分け、全候補・分単位の表現を維持したメモリ表現を検証する。メモリ増量だけで既存の1 CPU／6 GiB受入を達成済みにしない。Cloudflare追加0、最終一括、定期backup保留・30日保管、試験導入範囲外を維持する。
