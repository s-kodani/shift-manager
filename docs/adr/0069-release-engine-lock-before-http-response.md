# ADR 0069: 処理終了後、HTTP応答の送信前にエンジンのロックを解放する

日付2026-10-13。対象WP-03／04・R-01・TS-API／OPT。基点35764901ae295775eb6c5f83dda12396abf89786。制約・目的関数・計算予算・初回認証・DOのfence／stop／結果採用順序は変更しない。

## 原因と採用した修正

基点の機能CIは`probe-container.mjs`の最後の改変結果`/check`でHTTP503になった。Python HTTPサーバーでは、エンジンが終了した後も`reply()`のsocket writeが返るまで`work_lock`を保持していた。クライアントがContent-Length分の本文を受信した時点では、サーバー側のwrite呼出しがまだ戻っていない場合がある。次の逐次要求がこの間に到着すると、終了済みの計算に対してBUSYを返してしまう。

結果またはサニタイズ済みエラーを決め、finallyでロックを解放してから応答を送信する。計算／独立検証／ベンチマークの実処理中は1件制限と503 BUSYを維持する。応答中のクライアント切断でも、終了した処理のロックを保持しない。処理中にDOの停止確認やジョブの所有権を解放する変更ではない。

## 検証と代替案

実loopback HTTPで、本文を送信済みの応答スレッドだけをEventで停止し、次の独立検証を送る。3経路×成功／入力エラー／内部エラーの9条件が修正前はすべて503 BUSY、修正後はすべて200となった。既存の処理中BUSY・health応答、エラー情報の非公開、別HTTP独立チェッカーによる改変拒否も確認する。

クライアントにsleepや503の自動再送を入れる案は採用しない。正常な逐次操作の受付順序をサーバーで修正し、CIを偶然通過させる待ち時間に依存しない。実処理中の要求を待ち行列へ入れる案も、既存の1件拒否の契約を変更するため採用しない。

実施結果（過去の私有資料・公開対象外）。CIログには503本文がなく、当該サーバーで503を返すのはBUSYの分岐だけである。決定的な再現と修正後の試験を根拠とし、以前のProxy初回ログイン接続断やCPの時間超過を同じ原因で解決したとは扱わない。Cloudflare追加0、定期backupの有効化保留と30日保管、MVP／G0〜G2の未完了を維持する。
