# ADR 0011: チーム管理者の解除を不変の操作台帳へ追加する

日付: 2026-10-11。状態: ローカル実装・試験済み。Cloudflareへの今回の配備は未実施。対象: WP-01／05、Q34／99。

## 判断と理由

企業管理者が担当企業のチームメンバーへ管理者権限を付与・解除する。付与は既存API、解除は`POST /api/companies/:company/teams/:team/admins/revoke`を使用する。両方とも`operationId`・`expectedRevision`・`userId`を必須とし、チーム管理者自身による権限の委譲は許可しない。

旧`product_operation`のkind制約と、その操作を参照する設定版・不変履歴を保持するため、migration0009で`team_admin_revocation`を追加する。親台帳を作り直してCHECKを拡張する案は、既存の外部キーと履歴への影響を増やすため今回採らない。新しい解除台帳には企業・チーム・実行者・対象・入力revision・fingerprintを保持し、更新・削除を拒否する。監査と企業revisionは既存の共通系列を使用する。

INSERTトリガーが現時点の企業管理者権限、enabled・初回変更状態、revision、同じチームのスタッフ所属を検査する。成功したINSERTが役割をstaffへ更新し、revisionを進める。監査INSERTを同じD1 batchに含め、最終監査失敗も全体をロールバックする。更新0行をSQL失敗と仮定しない。[D1 batchの公式仕様](https://developers.cloudflare.com/d1/worker-api/d1-database/#batch)に沿い、workerdで競合・途中失敗を検証した。

同じ操作の再送は新しい解除を実行しない。後から再付与した後の過去解除再送でも、再付与状態を維持する。変更された内容や既存付与操作IDの再利用は拒否する。解除後はスタッフ所属・資格・入力とログイン状態を保持し、APIが毎回現在の所属権限を照合する。企業管理者権限自体の解除や、アカウント停止、スタッフ所属のない独立管理者のスタッフ化は今回の操作に含まれない。

## 結果と制約

実施記録（過去の私有資料・公開対象外）にAPI・原子更新・同じセッション・PC／モバイル画面の結果を残す。新しいライブラリ・認証方式は採用していない。Cloudflareへのmigration適用・配備、全業務APIの完成、アカウント停止と実運用、編集・公開・MVP受入は未完了。台帳が二種類になるため、将来の操作履歴一覧では双方を共通の企業revisionと監査で追跡する必要がある。
