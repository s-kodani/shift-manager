# ADR-0005: 製品の企業・チーム・スタッフと設定版

日付: 2026-10-10。状態: 限定実装・ローカル／専用Cloudflare PoC試験済み。MVP完成／G0通過ではない。

## 対象と正本

WP-01／02を進めるため、架空の原子更新・権限プローブから製品データを分離する。設計0.10の3章、Q99・100・106・107・118・119を参照する。確定要件は変更しない。今回の設定版は週開始曜日・希望締切日・半日区切り・役割比率端数処理だけを扱い、勤務ルール・契約・習熟度・計算入力の全体版を実装したとは扱わない。

## 実装した判断

- D1に企業、企業管理者、企業付きチーム、スタッフ、チーム所属を追加する。企業管理者は企業内の全チーム、チーム管理者は担当チーム、スタッフは本人だけ。運営者への日常のデータ閲覧権は追加しない。
- スタッフ番号は企業内で一意の文字列にする。同番号は別企業で使える。メール／名前で既存スタッフを照合しない。企業・チーム・スタッフ・本人アカウントの複合外部キーで別企業／別チームへの参照を拒否する。
- 企業単位の`revision`で関連マスタ更新を直列化する。条件付きUPDATEの0行を失敗とみなさず、操作INSERTのトリガーで版・現時点の権限・初回変更状態・昇格対象を検査し、失敗をSQL例外にする。操作、認証アカウント、スタッフ／所属、版更新、監査を同じ`DB.batch()`で更新する。
- `operationId`と正規化した要求・実行者・対象・種別を結び付ける。同じ要求の再送は重複せず、同IDの異なる要求は409。初期パスワードは成功した最初の応答だけに返す。要求・操作・監査には保存せず、再送はnull。応答は`no-store`。
- Better Auth 1.7.7の`better-auth/crypto`でハッシュを生成し、固定したnative SQLiteスキーマにユーザー／credential accountを同一バッチで作る。nativeアダプターのISO日付形式と`user`ロールを用いる。後続のSQL失敗で認証アカウントだけ残る状態を防ぐため、分散した作成・補償削除より原子性を優先した。依存更新時はスキーマ・ハッシュ・日付表現と実ログイン／初回変更を再検証する。
- 企業・最初の管理者の作成は運営者用サーバー関数で実装する。公開HTTPの申込み／管理者作成は閉じたまま。スタッフ発行は製品APIで行い、初回変更前は業務APIを拒否する。`/api/access`は本人の変更必須状態だけを返す。
- カレンダー設定は適用開始月と作成版を持つ追記式レコードにする。対象月以前の最新の適用開始月、その月内の最新の版を選ぶ。未登録はnullで暗黙の初期値を使わない。旧設定・操作・監査のUPDATE／DELETEを拒否する。

## 代替案と残る制約

行／月ごとの版は競合を減らせるが、まず企業内の関連更新を1つの版で守る。担当外チームの更新でも再読込が必要となる。分割時には読み取り集合と入力スナップショットの一貫性を証明する。現在の企業版は計算入力全体の保存版ではない。

Q118の公開済み月の再検証、当時の入力・設定・結果の結合、勤務ルール／契約の適用月、希望締切と対象月の対応／月末補正は後続で実装する。設定保存だけで公開・再計算を許可しない。スタッフ停止・権限解除・運営者の実運用コマンドと回復手順、認証UI、CSV、非同期ジョブは未実装。

## 技術資料と証跡

Cloudflareの[D1 batchとロールバック](https://developers.cloudflare.com/d1/worker-api/d1-database/)、[Workers実装指針](https://developers.cloudflare.com/workers/best-practices/workers-best-practices/)、公式Workers型`5.20261010.1`と既存Wrangler `4.149.0`の型／設定を確認した。スキル内の古いD1 Session例の`close()`は現行公式型にないため使用しない。実施記録（過去の私有資料・公開対象外）を参照する。
