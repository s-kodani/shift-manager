# ADR 0008: 非同期計算、配送待ちとコンテナの実行制御

日付: 2026-10-10。状態: WP-04基盤の実装・小規模実環境試験済み。G0、全条件モデル、MVP受入・運用性能の判定は未完了。

## 要件と判断

Q104の同一チーム通常1件は、受付済み・待機・実行・取消処理中を通じて適用する。計算完了では公開しない。履歴不足の参考案は公開禁止のまま扱う。製品の勤務条件・固定対象・優先順位は変更しない。

D1の`compute_job`の部分一意インデックスで企業・チームの活動中ジョブを1件に制限する。入力スナップショットを参照し、受付と配送待ち・監査を同一batchで確定する。DBトリガーで受付時の権限と現行入力版を再確認し、同じ操作IDの再送は元ジョブを返す。ジョブ作成・取消によって入力の企業版を進めない。

Queuesへ渡すのは形式版・企業ID・チームID・ジョブIDだけ。入力版やR2キーを配送本文から信頼しない。送信・受付の不明応答に備え、配送待ちをD1に保持し、PoCの毎分Cronで再送する。送信後のクラッシュや配送期限切れでも、活動中の配送義務を残す。取得競合の0行更新は敗者として扱い、SQL例外とは仮定しない。

同じ企業・チームは同じContainer Durable Objectへ送る。オブジェクト内の実行中RPCは、リースが切れても別の実行へ置き換えない。SQLiteに実行情報を先に保存し、オブジェクト再起動後に残っていた処理は停止確認後にD1の試行を回復する。DBの期限切れだけで再起動しない。初期はSIGKILLと`monitor()`、現在のrunningフラグで停止を確認した。後続の最小runtimeの実環境検証（過去の私有資料・公開対象外）で、停止は`destroy()`の完了とrunning=falseを確認する方式へ更新した。10秒の期限は維持する。停止未確認時はD1の活動中状態と永続情報を保持する。

`/solve`からの案は、同じ凍結入力を使った別の`/check`呼び出しで検証する。ソルバー内の検証結果をそのまま採用しない。履歴不足は`HISTORY_UNVERIFIED`、解未発見・解なし・モデル異常はソルバー状態と別々に記録する。結果はR2へ先に保存し、D1でジョブID・試行・実行トークン・期限・現行入力版・権限を再確認して参照を確定する。競合や取消で不採用になったオブジェクトは、未参照と証明するGCを実装するまで残す。

## 状態と初期の技術設定

| 状態 | 意味 |
| --- | --- |
| QUEUED | 配送待ち／停止確認後の再試行待ち |
| RUNNING | 実行権を取得。起動・計算・独立チェック・結果保存を処理中 |
| CANCELLING | 取消要求済み。処理終了・停止確認までチーム排他を保持 |
| SUCCEEDED | 案と独立検証を保存済み。公開可能を意味しない |
| NO_SOLUTION | 案がない終了。UNKNOWN／INFEASIBLEを別のsolverStatusで区別 |
| STALE | 現在の入力と一致しないため採用しない |
| FAILED | 実行・形式・独立検証・権限等の失敗 |
| CANCELLED | 待機取消、または実行中の処理終了／停止確認後の取消 |

最大3試行、実行権180秒、Container通信全体150秒、停止確認10秒、結果8MB／checker要求4MBは初期の資源設定であり、製品の対応規模・5分達成を保証する値ではない。既存Pythonサーバーの探索予算20秒もPoC設定のまま。PoCはstandard-2・最大1台、Queue consumerも最大1並列。企業間の資源枠の受入は別途必要。

結果の`inputSha256`はWorkerが送ったJSONのバイト列、`snapshotSha256`は元のR2入力、ソルバーの`inputHash`はPythonの正規化JSONを対象とする。異なる直列化のハッシュを一致したものとして報告しない。企業・月・設定版・入力版・ジョブ・試行の照合と独立検証を併用する。

## 代替と検証

D1リースだけの排他は、期限切れ後も古いプロセスが動く可能性があるため採用しない。DOのメモリだけの排他も、クラッシュ後に失われるため採用しない。チーム制御DOとContainer制御DOの分離は将来の実行資源拡張時に再評価する。今回は同じオブジェクトで順序と停止を管理する。

初回実環境試験は旧同期PoCのインスタンスが1台の枠を占有し、3試行で失敗した。現在状態を読み取って旧インスタンスを特定し、SIGKILLと終了監視で解放した。初回の停止操作は500で停止を確認できず、その応答を解放成功と扱わなかった。修正後はQueues経由の重複配送でも試行1回で計算・独立チェック・R2保存・停止を確認した。

後続の実Queues試験では、計算中に取消を要求し、CANCELLED・結果なし・停止まで確認した。再起動・異常停止試験（過去の私有資料・公開対象外）では、リセット後の旧プロセス継続と停止確認後の再試行、コンテナ異常停止後の成功を実測した。D1リースやメモリだけの排他を採用しない理由を裏付ける小規模証跡となる。取消処理中の新規受付競合・古いコールバックの実配送・DB／R2障害、配送送信直後の障害、各停止方式の反復計測、運用監視・GC・公開後再配置は受入前に残る。ローカルの注入試験を、実環境の障害復旧演習に読み替えない。

実施記録（過去の私有資料・公開対象外）、[Queuesの配送保証](https://developers.cloudflare.com/queues/reference/delivery-guarantees/)、[再試行・個別ack](https://developers.cloudflare.com/queues/configuration/batching-retries/)、[Containerのsignal／monitor](https://developers.cloudflare.com/containers/api/durable-object-container/)を参照。
