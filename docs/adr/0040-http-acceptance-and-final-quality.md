# ADR 0040: 登録済み500人のAPI受入と最終評価の記録

2026-10-12。状態: 限定したAPI受入を採用・検証済み。実施記録（過去の私有資料・公開対象外）。製品条件、権限、段階目的、150秒の計算通信期限、バックアップ有効化保留は変更しない。

## 検証の不足と選択

ADR 0039の登録済み試験は業務関数を直接呼び出し、初回変更フラグの解除もfixture内で行った。最終の独立証明を保存しているが、計測ログは初期案の評価だけだった。これでは登録・計算・公開をつなぐAPIと最終品質の受入には足りない。

新しい明示実行`test:compute-http-native`は、同じ架空operational-v1を製品のHTTP handlerへRequestとして渡し、Better Authのログイン・初回変更、Origin、入力・CSV・履歴・通常コンパイル、受付・配送待ち、結果取得、手動固定・再計算、公開・本人限定照会・通知をつなぐ。会社の初期発行のみ既存のprovision関数を使い、運営者の認証／引渡しは別の受入とする。管理者と1スタッフは初回変更を実行し、フラグをSQLで解除しない。

Honoの`app.request`を使うin-process HTTP handler試験で、ブラウザーや外部TCP経由の製品APIではない。Queues送信先を捕捉し、通常consumerへ配送を渡す。DO RPCを実`executeJob`と`checkDraftCandidate`へつなぐ制御アダプターにし、solve／別checkだけは実DockerのHTTPで実行する。これは実Queuesの配送特性・DOの残存フェンスや実停止の受入を置き換えない。既存の実環境・故障試験と合わせ、後続の全導線受入を行う。

## 最終評価と公開

HTTPで読んだ保存済み`validation`の状態・違反・不足・目的の順序／ベクトルを検査する。初期案を採用した場合は最終値が初期値から辞書順で退行していないことを検査する。検証済みの手動fixtureを参照として別に保存するが、ソルバーの答えや探索ヒントへ流用しない。再計算と手動案の比較は記録し、常に手動案以上になる仕様を勝手に追加しない。

通常不足を管理者が確認する公開操作を検査する。不足が残る場合は未承認の公開を拒否してD1未確定を確認し、明示的な承認後に公開する。公開時の別checkと公開証明が元の最終評価に一致し、本人には31日分だけ返り、全員の証明・例外が出ないことを検査する。受付／配送の再送と公開再送で計算・通知を重複させない。

通知対象は有効なチーム所属者で、このfixtureではスタッフ500人。会社管理者を加えた資格情報501人の終了とは別に数える。全資格情報・セッション・パスワードの終了と、runnerが所有Dockerを停止したことを確認する。メール送信・バックアップ取得・クラウド資源の変更は行わない。

実施結果: 500人の1ケースが合格した。最終評価の記録により、固定再計算のcombined 258,000が手動参照224,000より悪い試行も検出した。VERIFIEDと品質達成を区別する。前の検証済み編集案を最新条件で再チェックして探索の初期案へ使う案は後続の技術候補で、現行実装へ未採用。採用時も業務を固定する制約へ変換せず、全候補と必須条件・目的段階を維持する。
