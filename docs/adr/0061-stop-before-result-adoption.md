# ADR 0061: 結果採用でチーム排他を解放する前にプロセス停止を確認する

日付2026-10-13。WP-04・Q104・R-02。製品仕様・ソルバー予算・試行上限を変更しない。

## 問題

`completeJob`はSUCCEEDED／NO_SOLUTIONへ更新すると、同一チームのactive job部分一意制約から外れ、leaseとoutboxを解放する。従来は正常結果の採用後にfinallyで`terminate`を実行していた。その停止確認のみ失敗したとき、DO fenceは残るがD1が終端状態となり、利用者が新しいジョブを受付できてしまう。停止待ち中の取消も終端状態に対して拒否される。既存の「transport失敗と停止失敗」の試験では、正常案／案なしのこの経路を確認できなかった。

## 判断

通常計算はsolve・別checkの後、`confirmProcessStopped`が完了してからR2結果保存とD1条件付き採用を行う。停止確認後に取消要求を再読込し、CANCELLINGなら結果をuploadせずCANCELLEDへ進む。後続upload中の取消・版変更・権限失効は既存の採用トリガーで拒否する。

停止を開始したかと、正常完了したかを別々に持つ。停止がthrow／timeoutなら、同じ呼出し内のfinallyで再停止して成功扱いへ変えず、例外をQueueへ返す。RUNNING／CANCELLING、lease、永続compute_fenceを保持する。停止開始前に生じた失敗・取消もfinallyで一度停止を確認してから、終了／再試行状態へ進む。停止済みの結果保存失敗は、旧プロセスが生きている失敗と区別して既存の最大3試行へ従う。

Queueの再配送は同じDOで旧fenceを読み、停止確認後に`recoverStoppedJob`で旧attemptをPROCESS_RECOVEREDとして終了し、同jobの次attemptへ進む。実行中RPCはBUSYで保護する。lease期限だけの解放、新jobへの自動置換、停止不明のまま成功採用は行わない。

## 代替と適用範囲

採用後の停止失敗をFAILEDへ書き換える方式では、成功応答や新規受付との間の窓を塞げない。D1終端状態へ別の停止フラグを追加して受付を制限する方式は、状態・復旧・監査の整合を複雑にする。既存のRUNNINGと永続fenceを使い、採用の前提に停止確認を含める。

公開前の再検証は既に停止後に証明を保存している。手動編集／取消checkはfinallyの停止確認を終えてから応答する。これらの順序を変更せず、関連回帰を合わせて検証する。コンテナ物理停止をCloudflare全障害下で保証したという判断ではなく、停止を証明できない場合の採用・受付を拒否する判断である。

実施結果・固定したlocal fault計画・未実施範囲は停止確認後の採用検証（過去の私有資料・公開対象外）を参照。Cloudflareはローカル受入後の最終一括、定期backupは保留、保管30日を維持する。
