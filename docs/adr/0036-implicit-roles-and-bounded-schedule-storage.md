# ADR 0036: 役割なしの導出と上限付き圧縮保存

2026-10-12。状態: 実装・ローカル検証・専用Cloudflare配備と構築測定。製品の探索ヒント／予算への採用、G0、MVP全受入は別途。製品要件・目的段階を変更しない。実施記録（過去の私有資料・公開対象外）。

## 役割変数

Q77／Q78／Q120の実稼働・単一役割を維持する。旧方式は各処理区間に「役割なし」と適格役割のBooleanを作り、その合計を処理Booleanと等しくした。新しい`implicit-none-v1`は適格な実役割だけを作り、`sum(roles) <= processing`とする。役割なしの分母は`processing - sum(roles)`で厳密に導出する。処理0なら全役割0、処理1なら単一役割か役割なし。資格を持つだけでは分母から除かない。

勤務候補・業務候補・役割なし・実役割を削らない。分単位の準備・移動、全勤務量、独立チェッカー、段階目的は従来通り。内部の`explicit-v1`を同値比較用に残す。通常HTTPの`legacy-first-v1`／20秒、構築の100万変数ガードは維持する。`roleEncoding`を成功・構築失敗の指標に追加し、構築停止の`termination`を私有benchmarkとCLI要約まで伝える。UNKNOWNをINFEASIBLEへ変換しない。

## 通信と保存

前版の架空500人60分v3の結果は、空白を除いたJSONでも約8.52MB、独立チェック要求は約6.12MBだった。私有benchmarkの要約成功だけでは通常の8MB結果／4MBチェック要求を通せない。SQLと復旧コピーの既存上限を一律に増やす案に代えて、保存表現を圧縮する。

- PythonのHTTP JSONは空白なし。`/check`の要求とWorkerの計算結果・チェック要求／応答は16,000,000バイト上限。`/solve`／私有benchmarkの入力は4,000,000、入力スナップショットは従来上限を維持する。
- 下書きHTTP入力は16,000,000。認証・企業設定・本人提出等の別ルートは変更しない。
- シフト結果・下書き・公開／取消・再検証の保存時は展開JSONを16,000,000バイトまで検査し、64,000バイト超をgzip化する。R2保存本文とD1のサイズは既存8,000,000上限（再検証source/inputは既存4,000,000）。小さいJSONは従来のまま。
- SHA-256・byte_length・取消元の版ハッシュは**実際の保存本文**を使う。読取は権限・サイズ・SHAを検査後、gzip magicを見て上限付きstream展開し、契約・企業／チーム・版を検査する。旧未圧縮JSONも読める。展開過多・壊れたgzipを拒否する。
- R2には`application/gzip`を設定し、`Content-Encoding: gzip`を付けない。復旧ツールの自動展開で本文とハッシュが変わることを避け、復旧コピーも不透明な保存本文として検査・転送する。ファイル名の`.json`で圧縮有無を判断しない。スキーマ移行・既存本文の一括書換えは不要。

WorkersのCompressionStream／DecompressionStreamのgzip対応は[公式Web標準資料](https://developers.cloudflare.com/workers/runtime-apis/web-standards/#compression-streams)と現在の型・workerd実行で確認した。上限はこのプロジェクトの技術判断で、Cloudflare製品上限や製品仕様ではない。展開上限を上げれば勤務人数対応やCPU／メモリ達成が保証されるとは扱わない。

## 検証範囲と保留

小規模の全18通りを両表現・業務／チーム・ceil／floorで独立照合する。通常D1/R2計算保存の大容量transport試験は制御したsolver／checkerを使い、実制約検証とは分ける。実Dockerの500人30分全月手書き案を`/check`へ送り、別に圧縮R2保存を照合する。下書き・公開・再検証・実半日取消の圧縮証明書、改ざん、展開上限、復旧コピーの本文完全性を試験する。

実Cloudflareでは新版のモデル構築を確認したが500人30分・120秒で有効案を得ていない。大規模通常Queues／UI全体・探索品質／時間配分・反復性能・G0〜G2は別の確認事項。定期バックアップの有効化保留、復旧コピー30日、Resend実配送disabledを維持し、これらの試験で定期取得・メール送信を実行しない。
