# ADR 0055: 計算入力のスタッフを企業内スタッフ番号順にする

日付: 2026-10-12。対象WP-02／03・入力再現性・TS-OPT／TS-PERF。確定製品仕様・目的の優先順位・計算予算・資源上限は変更しない。

## 観測

休憩編集試験（過去の私有資料・公開対象外）の500人通常計算は、有効案とUNKNOWN／NOT_RUNに分かれた。終了済みの実D1／R2を読み、各ジョブのスナップショット本文のSHAと長さを照合した。UUIDなどの識別情報、スタッフ・履歴・予定参加者の並びだけを正規化すると、勤務条件・需要・役割・希望・履歴の値は一致する。一方、旧コンパイラーの`ORDER BY id`によるスタッフ順序は異なる。

`initial_hint.py`と`interval_hint.py`は入力内のスタッフ順を休憩分散・同点候補・担当配分の初期値へ使う。UUIDは登録時にランダム生成されるため、同じ論理条件の再登録で初期値まで変わる。順序差が探索未発見の原因であることはまだ証明していない。構築時間・ホスト負荷・残り予算も調査対象とする。

## 判断

通常コンパイラーのスタッフ参照を、企業内で一意のスタッフ番号の`COLLATE BINARY`による昇順にする。企業・チームの絞り込み、スタッフIDを用いた契約・スキル・希望・履歴との結合は維持する。スタッフ番号を数値へ変換したり、先頭0を除いたりしない。全候補・必須条件・各希望の同じ重み・段階目的・独立検証は維持する。勤務不可や業務・役割を固定する変更ではない。

既存スナップショットの本文とSHAは不変。新しい入力の通常コンパイルにこの順序を使う。過去の入力を再解釈して書き換えない。番号変更があればその入力条件を保存した版として扱い、別の番号順で以前と同じ計算結果になる保証を追加しない。

代替として、UUID順を維持する案、ソルバーでスキル等から別の順序を作る案を検討した。前者は再登録による揺れを残し、後者は今回は別のヒント方式の導入になる。まず通常の企業内識別番号で入力の再現性を整える。探索方式の変更や性能達成と同一視しない。

## 検証と範囲

実D1の回帰では、番号順がUUID順の逆になる架空データを用意し、個人別ルール・スキル・希望・予定、別チームの除外、旧スナップショットの不変性を確認する。保持した500人失敗入力から、元順序／番号順の2ケースだけを同じnativeイメージ、120秒・1 CPU／6 GiB・追加swapなしで比較する。順序変更以外の値を変えず、別HTTP独立検査と終了証跡を保存する。実施記録（過去の私有資料・公開対象外）で成功・未発見・未実行を区別する。

直接HTTPの順序比較は、製品の実SDK・大規模編集／固定／取消／再配置の受入ではない。安定性・品質と全UIを確認してから最終Cloudflareの対象を凍結する。Cloudflare追加配備・計算は行わず、定期backup有効化保留・30日保管・通常メールdisabledを維持する。
