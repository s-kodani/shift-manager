# ADR 0057: 日別勤務候補から継続変数の等価な上限を導く

日付: 2026-10-12。対象WP-03／TS-OPT・PERF。CP内部の時間超過（過去の私有資料・公開対象外）を受けた技術候補で、通常採用・性能達成・MVP完成は未判定。

## 候補の変更

各スタッフ・日・業務の継続量`run`は従来`0..1440`だった。候補は、その日の有効な全勤務候補それぞれの実稼働分集合`A_i`から`U = max_i |A_i|`を求め、`0..U`とする。勤務候補の削除、時刻の丸め、最低継続や勤務量の緩和は行わない。

集合には準備・移動分を含め、休憩・取消・研修／会議分を除く。研修／会議は勤務量へは算入するが業務の継続量へ算入しない。休憩・予定越しの同業務継続を分断しない既存制約、勤務・休憩の明示固定と理由付き例外、公開後の取消以外の維持はそのまま。

`tight_run_bounds`の既定はFalse。固定診断プロファイル`mvp-joint-tight-run-bounds-v1`だけTrueにし、120秒・v4の初期案・全モデル・段階目的・presolve／seed／worker数を維持する。任意の値はHTTPから注入できない。Workersの通常要求`mvp-joint-v1`と結果採用条件は変更しない。

## 等価性の根拠

1. その日の候補選択変数`x_i`にはexactly-one制約がある。したがって、配置枠`b`の長さ式`L_b = Σ_i x_i |A_i ∩ b|`は、選ばれた候補`j`の実稼働分数となる。
2. 枠は重ならず、可能な全実稼働分を覆うため、全枠の長さの和は`Σ_b L_b = |A_j| ≤ U`。イベント等で分断される部分枠も整数分で数え、和を30／60へ丸めない。
3. 継続変数は業務非選択で0、開始／切替で`L_b`、同業務の継続で前の継続量＋`L_b`。長さが非負なので、帰納的にすべての継続量は選択候補の枠長の部分和であり、`0 ≤ run ≤ |A_j| ≤ U`。
4. よって元モデルの全充足解は新上限をすでに満たす。新モデルは上限以外を変えないため逆方向の包含も成立し、実行可能な勤務・業務・役割と目的評価は同じである。実稼働がない日は元から継続変数を作らない。

勤務候補の実稼働集合の**和集合の大きさ**を上限に使う必要はない。例えば180分の拘束から位置の異なる30分休憩を引いた候補は、全候補の和集合180分でも、1候補の上限は150分。複数候補の同時選択を許す将来変更がある場合、この根拠は再確認する。

## 検証と採用判断

- 30／60分枠で、準備・7分研修の部分枠・会議・固定休憩・公開済み取消・全時間研修・固定勤務不可例外を正解比較する。最初のCP呼出し前の全protoを比較し、run domain以外の変数・制約・目的・ヒントが同じことも確認する。
- 複数勤務パターン／自動休憩の位置、役割・丸め・目的順・初期方式を全列挙の独立チェッカーと比較する。残る60分に最低継続61分という矛盾は両方式で拒否する。
- `npm run test:compute-run-bounds-native -- manifest.json image-sha256`で保持した全500人の固定入力SHAを照合し、同じimage・1 CPU／6 GiB・追加swapなしで通常／候補を各1回測る。別HTTPチェック・kernel観測・所有コンテナ終了を含める。エラー時に自動再実行しない。
- 全列挙の合格は等価性の補助証拠であり、速度・資源・実SDK・Cloudflare互換性の証明ではない。反復品質・資源余裕と全導線の受入は別に残す。計測結果は実施記録（過去の私有資料・公開対象外）へ残す。

代替案の全体予算／資源の無条件拡大、勤務候補削減、最低継続の変更は採用しない。前処理なしの候補も通常採用せず、今回は上限の等価変更だけを比較する。
