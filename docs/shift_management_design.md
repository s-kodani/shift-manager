- 日付をまたぐ勤務。

- 当日の業務量変動に追従するリアルタイム再配置機能。

- 勤怠・人事システムとのAPI連携。

- 業務配置の明示固定、時間単位の休暇・欠勤、業務配置や不足集計のExcel・CSV出力。
- 研修・会議の開催時刻の自動決定。
- 事務処理を複数の時間帯に分散させる期限内処理計画。
- 公平性・人件費を独立した最適化目的にすること。

## 4. 勤務・業務配置の要件

### 4.1 スタッフ情報と希望

スタッフ本人がアプリから勤務可能日・勤務不可日時・希望を登録する。

| 情報 | 自動配置での扱い |
| --- | --- |
| 勤務不可日時 | 配置しない必須条件 |
| 希望勤務日・休日 | できるだけ満たす評価条件 |
| 希望時間帯・勤務パターン | できるだけ満たす評価条件 |
| 勤務契約の曜日・時間帯 | 必須条件 |
| スキル・習熟度 | 業務の担当可否と処理能力に反映 |

企業共通の毎月の締切日を設定する。締切後は管理者が受付を再開した期間だけ本人が変更できる（Q88〜89）。本人による希望の強さは設けず、すべて同じ強さとする。未提出は希望なしとして通常どおり配置する（Q86〜87）。

希望は登録項目ごとに1件として採点する。同日に勤務希望と勤務パターン希望があれば各1件、両方充足なら2件とする。希望時間帯は勤務があり、その出退勤が希望範囲内に収まれば充足とし、部分点は設けない（Q90〜91）。設計案として、希望充足率の分母は採点対象の登録希望件数、分子は充足件数とする。希望0件は「希望なし」と表示し、100%と表示しない。2026-10-11の確定回答により、企業共通日を対象シフト月の前月へ適用し、存在しない日は前月末に補正する。指定日23:59の分まで日本時間で受け付け、翌日00:00から締切後とする。元の企業設定日は変更しない。本人の勤務不可日時にも、希望と同じ締切・管理者の受付再開を適用する（2026-10-11補足回答）。企業管理者または担当チーム管理者がチーム・対象月を指定し、現在から終了日時まで追加で受け付ける。通常の締切前の受付は、追加受付の終了操作で停止しない。保存時に期限・本人・設定版・固定版をサーバーとDBで検査する。

### 4.2 勤務ルール

企業共通、雇用区分別、スタッフ個別のルールをすべて同時に満たす。個別ルールによって上位ルールを緩めることはできない。

必須ルールは以下のとおり。

- 日・週・月の勤務時間上限。
- 月単位の最低勤務時間・最低勤務日数。勤務不可・承認済み休暇でも自動で引き下げず、満たせなければ矛盾を表示して管理者が設定を調整する。
- 連続勤務日数上限。
- 月単位の休日数下限（Q73）。
- 契約で定めた勤務曜日・時間帯。

設計案として、上限が複数ある場合は最も厳しい上限を適用し、休日数の下限は最も厳しい下限を適用する。勤務可能曜日・時間帯は各階層の共通範囲とする。矛盾して勤務可能範囲がなくなる場合は、計算前に設定矛盾を表示する。

週の開始曜日は企業ごとに設定する。勤務時間の上限・下限の集計は休憩を除外し、研修・会議・準備・移動を算入する。最低勤務時間・最低勤務日数は月単位のみとする。休日数の下限は月単位。休憩・勤務取消を除く勤務時間があれば、研修・会議・準備・移動だけの日も最低勤務日数の1日と数える（Q73〜74）。設計案として、その暦月で勤務日と判定されない日を休日として集計する。勤務ルール・契約は適用開始月を指定し、公開済みの対象月は再検証する。過去の版と当時の検証結果を保持する（Q118）。

### 4.3 業務・スキル・役割

- 時間帯ごとに業務を切り替える。
- 業務ごとに最低習熟度を設定し、未達のスタッフは担当不可とする。
- 担当可能なスタッフには、習熟度に応じた処理能力係数を設定する。
- SV・リーダーは最低人数とスタッフ数に対する比率の両方を設定可能とする。
- 一般業務との兼任可否は役割・業務ごとに設定する。
- 同じ業務を続ける最低時間を設定する。
- 業務切り替え時の準備・移動時間は、切り替え元・切り替え先の業務の組み合わせごとに設定する。

役割条件はチーム全体と業務別の両方に設定する。最低人数と比率による人数の多い方を必要数とし、比率の端数処理は企業ごとに設定する（Q76）。切り上げ・切り捨てを設定候補とする設計案であり、初期値・選択可能な丸め方式は詳細設計で確定する。

比率の分母は同時刻に一般業務へ稼働している実人数。ただし、兼任中のSV・リーダー自身は除く。休憩・会議・研修・準備・移動中も除く（Q77）。資格を持つだけの人と、当該時刻に役割を担当する人を区別する設計案とする。

チーム全体・業務別とも、一般業務を処理中の役割担当者だけを役割人数に数える。管理専任者は数えず、業務別では担当している1業務だけに数える。SV・リーダーの両資格があっても同時刻に計数できる役割は1つだけ（Q78・Q120）。同じ担当者をチーム全体と所属業務それぞれの条件で参照することは、複数業務への重複計数とは区別する設計案。

習熟度の段階は企業共通、各段階の処理能力係数は業務ごとに設定する（Q119）。具体的な段階数・名称・係数・最低習熟度は企業／業務の設定データであり、本書で一律の数値を指定しない。

### 4.4 休憩・研修・会議

- 勤務パターンで時刻を固定する休憩と、許容時間帯から時刻を自動決定する休憩に対応する。
- 出退勤・休憩は30分単位とする。
- 研修・会議は管理者が日時と参加者を指定する。
- 休憩・研修・会議中は通常業務の処理能力に算入しない。
- 準備・移動時間は勤務時間に算入するが、通常業務の処理能力には算入しない。切り替え先の30分／60分配置枠の先頭から確保する。例えば60分枠で30分必要なら、先頭30分が準備・移動、後半30分が通常業務となる。

必要休憩時間は勤務時間に応じたルールで決定する。算定基準は休憩を除いた実働時間／出勤から退勤までの時間から企業ごとに設定する。固定休憩は必要量以上を許容し、自動休憩は必要量と一致させる（Q130）。元の固定／自動の種別は公開後も保持する。自動休憩は分割せず連続取得し、取得可能範囲は勤務開始・終了からの相対時間で設定する。公開後は固定・自動いずれの休憩時刻も維持する。

自動休憩は全体を取得可能範囲内に収める（Q75）。研修・会議は参加者が全時間に参加できる勤務パターンを必須とする（Q83）。勤務条件や固定休憩と矛盾する予定の登録は拒否し、条件調整後に登録する（Q110）。登録時に未固定の勤務・自動休憩を選べる場合はその実現可能性を検証する設計案とし、確認できないものを登録可能と断定しない。勤務取消時の参加登録解除は第7章の別処理とする。閾値・休憩分数・相対範囲の具体値は企業設定として整備する。

### 4.5 配置枠・時刻・分単位計算の関係

通常業務の選択枠は30分または60分、出退勤・休憩は30分単位。準備・移動・最低継続時間は分単位で正確に扱い、30分へ切り上げない（Q80・Q113）。内部全体を30分枠だけで判定する旧案は採用しない。

設計案として、配置枠、出退勤・休憩、予定、取消、準備・移動の開始終了などの状態変化で時間区間を分割し、各区間の長さを整数分で保持する。1分の密な計算枠と、状態変化点による可変長区間をA1で比較し、分単位の正確さと性能を両立する方式を選ぶ。

準備・移動は切り替え先の配置枠の先頭から確保し、その開始から切り替え先の最低継続時間へ算入する（Q79）。休憩を挟んでも同じ業務なら継続し、休憩時間は数えない。研修・会議を挟んでも前後が同じ業務なら継続し、その時間は継続から除外する（Q123）。準備・移動は連続して確保し、休憩・研修・会議と重なる切り替え位置は選ばない（Q125）。勤務開始時の初回準備は不要（Q126）。準備・移動は業務配置1枠以内のみ登録でき、超える値は拒否する（Q127）。チームの配置枠変更時もペア設定を再検証する。

例：60分枠の先頭10分が準備、残り50分が能力1.0の通常業務なら、処理能力量は50/60人時間。最低継続時間には準備を含む60分を算入する。必要能力1.0が全枠にある場合の不足は先頭10分の1/6人時間であり、残りの能力で相殺しない。枠内に休憩があれば、その時間は勤務時間・通常能力・最低継続時間から除外する。

平均処理量と瞬間的な稼働人数を別に評価する。電話の応答水準や役割人数を1時間平均だけで満たしたと判定しない。

## 5. 業務量と必要人数

### 5.1 入力

- 必要人数の直接入力。
- 業務量からの必要人数算出。
- 業務量予測値の画面入力、Excel・CSV取り込み。

直接入力する必要人数は、習熟度を考慮した処理能力換算人数とする。直接入力がある場合は管理者の入力を優先し、業務量からの算出値は参考表示する。60分枠の需要値は前半・後半の30分へ同じ値を適用する。準備などでさらに分割した区間にも、その需要枠の同じ必要能力を適用する設計案。30分配置時は30分の需要枠を設定する入力案とし、60分予測の変換・集計方法は詳細設計で確定する。直接入力の0は入力済み値として扱い、未入力と区別する設計案とする。上書き履歴、能力係数の基準、精度・丸め方法は未確定。

### 5.2 対象業務

| 業務 | 算出に使う情報 | 確定した処理範囲 |
| --- | --- | --- |
| 電話 | 入電数、平均処理時間、目標応答水準 | 時間帯ごとの要員需要 |
| 事務 | 件数、標準処理時間、処理期限 | 業務量を登録した時間帯内で処理 |
| チャット | 件数、処理時間、同時対応数 | 時間帯ごとの要員需要 |

算出アルゴリズムは未決定。電話の待ち行列モデル、放棄呼の扱い、チャット同時対応時の実効能力などは、業務データと前提を確認して選定・検証する。

設計案として「実人数」「スキル別人数」「処理能力」を別の指標として保持する。例えば新人2人の処理能力合計が熟練者1人分であっても、SV1人の要件を代替したことにはしない。

### 5.3 不足の表示

一般スタッフ・必要スキル・SV・リーダーの不足は可視化し、管理者が判断する。不足を理由に勤務不可や勤務ルールを自動で緩めない。

表示案は、日付・時間帯・業務・必要数・配置数・不足数・不足能力・役割不足を一覧とする。需要を満たす解がないことと、必須条件を守る解がないことは区別する。

## 6. 最適化モデルの設計案

### 6.1 決定対象

| 決定変数の概念 | 意味 |
| --- | --- |
| 勤務パターン選択 | スタッフ・日付ごとの勤務パターン／休日 |
| 業務選択 | スタッフ・日付・30分／60分枠ごとの担当業務 |
| 自動休憩位置 | 設定された許容範囲内の休憩時刻 |
| 不足量 | 時間帯・業務・スキル・役割別の需要未充足量 |

初期案では同時刻に複数の一般業務を担当させない。チャットの同時対応数は同一業務内の能力として扱う案であり、複数業務の同時兼務を意味しない。

### 6.2 必須条件と評価条件

| 条件 | 自動配置 | 手動編集後の公開 |
| --- | --- | --- |
| 勤務不可日時 | 新規自動配置では必ず守る。理由記録済みの固定例外だけ維持 | 理由を記録した例外のみ可 |
| 勤務時間上限 | 必ず守る | 違反公開不可 |
| 月の最低勤務時間・最低勤務日数 | 必ず守る。満たせなければ矛盾を表示 | 違反公開不可。条件調整後に再検証する設計案 |
| 連続勤務上限・休日下限 | 必ず守る | 違反公開不可 |
| 契約曜日・時間帯 | 必ず守る | 違反公開不可 |
| 最低習熟度 | 必ず守る設計案 | 例外公開の対象に含めない設計案 |
| 休憩・重複禁止・固定予定 | 必ず守る設計案 | 例外公開の対象に含めない設計案 |
| 最低継続時間・切替時間 | 必ず守る設計案 | 例外公開の対象に含めない設計案 |
| 必要人数・スキル充足 | 不足を減らす | 不足を警告し管理者判断 |
| SV・リーダー充足 | 不足を減らす | 不足を警告し管理者判断 |
| 勤務日・休日・時間帯の希望 | できるだけ満たす | 未充足を確認可能 |

最低習熟度などの詳細な違反公開ルールは、設計案であって直接の回答事項ではない。勤務不可以外の例外を新たに認めることはしない。

### 6.3 評価方法

希望／充足優先はチーム・計算実行単位で1つに統一する。業務別には役割先行／同段階を設定する（Q122）。必須条件はどの方式でも守る。

| 方式 | 評価順序 |
| --- | --- |
| 人数・スキル充足優先 | 不足評価の最小化 → 先行値を悪化させず希望未充足の最小化 → 同等なら余剰削減 |
| 希望優先（Q85） | 希望未充足の最小化 → その値を悪化させず不足評価の最小化 → 同等なら余剰削減 |

希望は登録項目ごとの等しい1件で採点する（第4.1節）。余剰は許容し、最低勤務量のための余剰を禁止しない。

一般業務は処理能力換算の不足量×時間、SV・リーダーは実人数の不足×時間を区間ごとに積算する。例えば10分の1人不足は1/6人時間。業務間は同等に扱い、業務の独立した優先順位は設けない（Q114）。役割不足との関係は①役割先行、②同段階を業務・チームごとに選ぶ。同段階では一般1人時間と役割1人時間を同じ重みで扱い、任意の重み設定を初期版に設けない（Q111）。

混在設定の合成は設計案として、役割先行対象の役割不足合計を第1段階、全業務の一般不足＋同段階対象の役割不足合計を第2段階とする。チーム全体の役割条件もチームの方式に従う。各段階内の業務の重みは同じ。業務別とチーム全体の役割条件は別条件なのでそれぞれ集計し、内訳を表示する。希望優先ならこの不足の段階より先に希望を評価する。希望／充足優先の業務別混在は採用せず、全体方式を1つ指定する（Q122）。

順位付き最適化では、後段で先行評価値を悪化させない。前段の最適性が未証明なら得られた値を保護して継続し、厳密な最適性を表示しない。余剰は通常業務能力の需要超過量×時間を削減する設計案とする。休憩・研修・会議・準備・移動等以外の勤務には担当業務を割り当て、担当のない待機は認めない（Q124）。数値精度・許容差、混在方式の詳細を独立チェッカーと小規模全列挙で検証する。人件費・公平性の独立した最適化は初期版に含めない。

### 6.4 計算終了と結果の扱い

通常計算は5分程度を目標とする。現時点で性能保証ではない。

| 状態 | 表示・操作の設計案 |
| --- | --- |
| 最適性が確認された | 案と評価指標を表示 |
| 制限時間に達したが必須条件を守る案がある | 現時点の案を表示し、採用・再計算を選択 |
| 制限時間内に案を発見できない | 未発見と表示。実行不可能と断定しない |
| 必須条件の矛盾により実行不可能と確認された | 条件の衝突を示し、修正を促す |
| ジョブが失敗した | エラーを表示し再実行可能にする |

最適化結果は公開前にも再検証する。通常計算の5分程度は、計算開始操作から検証済みの案が表示されるまでの総時間を対象とし、待機・前後処理・検証・表示を含め、AI説明は除く（Q103）。300秒を総時間の目標値として測り、探索に300秒すべてを割り当てない。各段階の予算と停止期限は実測に基づいて設定する設計案。同じチームの通常計算は1件までとし、実行中は次の通常計算を開始できない（Q104）。多重送信・別管理者からの要求もサーバーで制御する。

履歴不足時は未検証の参考案として表示できるが、履歴確認・再検証まで公開できない（Q81）。ソルバーの終了状態と「検証済み／未検証／違反あり」を別に保持する設計案。参考案を完全に必須条件を守るFEASIBLE案として表示しない。

### 6.5 月・週の境界

連続勤務日数や週の勤務時間を正しく判定するため、計算対象月の前後にある確定勤務も境界条件として参照する設計案とする。対象期間外の勤務は勝手に変更しない。

必要な前月履歴が不足する場合は未検証の参考案を作成できるが、履歴確認・再検証まで公開できない（Q81）。翌月が未確定なら確定済みの勤務だけを参照し、未確定分は翌月作成時に前月勤務を含めて検証する（Q98）。翌月仮シフトの同時計算は行わない。必要履歴範囲は週開始曜日・連続勤務上限などから導出する設計案。

## 7. 操作・公開・休暇承認フロー

### 7.1 公開前

1. 管理者がスタッフ・スキル・契約・勤務パターン・需要・ルールを登録する。
2. スタッフが勤務可能日と希望を登録する。
3. 管理者が条件と優先順位を指定して計算する。
4. 不足・希望充足・必須条件違反を確認する。
5. 必要に応じて手動編集し、維持したい配置を固定する。
6. 再計算または公開前チェックを行う。
7. 管理者が直接公開する。
8. スタッフ向けのお知らせを作成する。

### 7.2 公開後の休暇・欠勤

取消単位は全日・半日のみ。半日の区切りは企業共通の時刻を設定し、勤務と重なる部分を取消対象とする（Q93〜94・Q109）。休暇・欠勤申請は所属チーム管理者が承認し、欠勤は管理者の直接登録にも対応する（Q95）。

1. スタッフ申請または管理者の欠勤直接登録を受け付ける。
2. 管理者が承認・確定する前に、対象の固定を明示解除し、取消後の月最低勤務時間・日数などを検証する。最低勤務量と矛盾する休暇は承認を止め、設定調整後に承認する（Q84）。実際の欠勤も事実は記録できるが、勤務取消の確定は止め、管理者の設定調整後に反映する（Q121）。自動の下限引き下げはしない。
3. 承認・確定時に勤務取消を公開済みシフトへ即時反映する（Q96）。取消区間に重なる研修・会議の該当スタッフの参加登録を自動解除し、履歴に残す（Q97）。設計案として、取消、参加解除、公開版更新、通知イベントを同じ業務更新単位にする。
4. その時点の不足を再集計して表示する。残る出退勤・公開済み休憩を維持し、業務配置の再計算案を作る。
5. 管理者が変更差分・不足を確認し、通常の検証を経て業務再配置の更新版を公開する。

取消の即時反映は、再配置案の自動採用・自動公開を意味しない。勤務取消は承認・確定条件を満たした時点で行う。未確定の欠勤事実は公開勤務を取消済みと表示せず、対応待ちとして管理者に示す設計案。

半日取消は、元の予定出退勤を履歴・基準として保持し、取消区間を非勤務として除外する設計案。勤務時間は取消と休憩を重複控除せず、残る勤務があれば勤務日1日とする。取消に重なる休憩部分も稼働能力は0であり、残る休憩の時刻を動かさない。取消後の必要休憩を再検証する。出勤〜退勤の時間基準では元の区間から取消を除く（Q128）。固定休憩は必要量以上なら許容するが、自動休憩は公開済みでも必要量と一致しなければ承認・確定を止める（Q130〜131）。休憩時刻を変更したり自動を固定へ変換して矛盾を解消しない。取消後の希望は残る勤務で再評価し、元パターンと勤務範囲が変われば希望パターン未充足とする（Q129）。通常の出退勤変更・時間単位取消・休みの人の追加出勤は扱わない。予定参加の自動解除は対象参加者だけに限り、全時間参加の条件が残る他の参加者には適用しない。2026-10-14補足（Q97・Q124）：取消に重なる研修・会議の参加全解除により、取消外の残る勤務が未割当になる場合は、承認・取消確定を停止する。公開勤務・受付・参加状態を維持し、管理者が先に予定参加と業務配置を整えて別途公開した後、同じ申請を最新条件で再確認する。未割当待機を許容せず、取消時の業務自動追加は行わない。

### 7.3 固定指定と衝突

手動修正しただけでは固定しない。管理者が固定指定した勤務パターン・出退勤時刻・休憩時刻だけ再計算で維持する。時間帯別の担当業務の固定は初期版の対象外（Q92）。

固定勤務への休暇は、管理者が明示的に固定を解除するまで承認できない。勤務と休憩の固定範囲について衝突を確認する。ほかの必須条件との衝突は表示し、固定を守るために勤務ルールを自動で破ることはしない。

勤務不可へ手動配置し、理由を記録して固定した勤務は、その固定配置だけを承認済み例外として再計算へ引き継ぐ。ほかの勤務不可への新規自動配置は認めない。例外の対象はスタッフ・日付・時間範囲・固定配置・理由へ限定し、包括的な勤務不可の解除として扱わない。

### 7.4 公開・履歴の設計案

公開版は変更前の内容を保持し、新しい版として更新する。誰が、いつ、何を変更したかと、例外理由を記録する。公開済みシフトを再計算ジョブが直接上書きすることは避け、結果は案として確認できる形にする。

許可済みの勤務不可例外以外の既知の必須条件違反がある手動編集は、下書きでも保存を拒否する（Q82）。履歴不足による未検証の参考案（Q81）とは区別する。ルール・契約の変更は適用開始月を保持し、公開済みの対象月は再検証する（Q118）。過去版を上書きせず、再検証で違反・未検証があれば以後の採用・公開を止める設計案。公開済みの時刻を自動変更して矛盾を解消しない。

### 8.1 画面共通の表示方針（2026-10-16ユーザー決定）

スタッフ管理では「企業共通ルール・雇用区分」と「勤務契約・習熟度・資格」を別カードに分ける。前者には共通ルールの参照・雇用区分の参照／編集／追加、後者にはスタッフ選択とその人の契約・習熟度・資格を置く。雇用区分の編集は企業管理者に限定する既存権限を維持する。実装・確認範囲（過去の私有資料・公開対象外）。

時刻を直接入力する欄は、コロンなしの数字4桁HHMM（例：0930）で入力する。0000〜2359と当日末の2400を扱い、追加受付の終了日時は日付と0000〜2359の時刻を分ける。分単位／30分単位／配置枠の既存制限を維持し、表示とCSV形式はHH:MMのままとする。[判断・対象範囲](adr/0126-numeric-time-input.md)。

製品画面全体を白・グレー基調の共通部品と余白で統一する。シフト画面の月間カード内ではタイトル下の内容まで24px（モバイルは共通カードの16px）、企業共通ルールの段階追加・保存ボタンの間には12px以上を設ける。段階削除は各段階の左端のマイナスアイコンとし、段階番号を読み上げラベルで示す。操作結果の通知は画面右下のトーストに表示する。成功・案内・警告・エラーはすべて5秒で終了し、ホバー／フォーカス中は一時停止する。入力エラー、公開可否、検証結果、応答未確認時の確認操作、履歴のお知らせは画面上でも確認できるようにする。

取得中はスケルトン、認証確認・保存や送信中はスピナーと説明を表示し、取得完了前に「データなし」と表示しない。同じ対象の再取得では既存情報を保持し、会社・チーム・月の切替では前の対象を表示しない。計算待ち・実行中・取消処理中を区別し、未計測の進捗率を表示しない。未保存入力の破棄は確認ダイアログで選べるようにし、ブラウザー離脱の確認も維持する。[判断と実装方針](adr/0121-tailwind-shadcn-product-ui.md)。

### 10.2 入出力

| 方向 | 対象 |
| --- | --- |
| 入力 | スタッフ、スキル、勤務契約、業務量予測 |

スタッフの再取り込みは企業内で一意のスタッフ番号で照合する（Q100）。プレビューで行別のエラーを表示し、管理者が全件中止または正常行のみ反映を選ぶ（Q101）。正常行の相互参照・重複・更新競合も確認する設計案であり、メールアドレスや同名を照合キーにしない。

### 10.3 時刻・バックアップ・復旧

初期版の勤務時刻・締切などは日本時間に統一する（Q108）。復旧目標はRPO最大24時間、サービス全体停止からRTO1時間以内（Q116〜117）。データ損失の許容範囲とサービス復旧時間は別に検証する。構成・費用・障害範囲を踏まえて復元、公開版・承認・履歴の整合、通常操作の再開まで実測する。目標の達成は未検証。日次バックアップを置くだけで両目標を達成済みとしない。ユーザーの2026-10-11の決定により、MVPの復旧用バックアップは30日保管する。勤務・監査履歴そのものの保存期間とは別であり、原本を30日で削除しない。[ADR 0027](adr/0027-backup-retention-and-integrity.md)に方式・実施結果を区別する。原本の保存期間、運営者アクセス、対応体制はA0の運用設計に残す。

#### AI-01：不足・配置結果の説明

**入力：** 対象チーム・シフト版・計算ジョブ、必要数・配置数・処理能力、スキル・役割不足、希望充足、勤務範囲・休憩・固定予定、検証済みの条件、計算終了状態。

**出力：** 配置案の要約、不足している時間帯と業務、確認すべき条件、根拠の数値・参照先、比較できるシナリオへの案内。

**説明例（架空のデータ）：**

> 10月13日15〜16時の電話対応は、必要18人相当に対して配置16人相当で、2人相当不足しています。この時間枠では担当可能なスタッフ3人が休憩・会議に入っています。休憩調整が許可される場合は、変更案を比較できます。

上記は状況説明であり、休憩が不足の原因であることの証明ではない。原因の断定や改善量の説明は、検証処理・条件分析・シナリオ再計算で裏付けられた範囲に限定する。

- 実人数、処理能力換算人数、SV・リーダー人数を区別する。
- 確認された事実、検証済みの制約、未検証の候補を分けて表示する。
- 特定できない理由は「特定できていない」と示し、推測で埋めない。
- 最適性未証明の案を「これ以上改善できない」と説明しない。
- 時間内の案未発見を「実行不可能」と説明しない。
- 30分／60分の需要枠と、出退勤・休憩・分単位の準備等を区別し、平均能力だけで常時在席を満たしたと判断しない。

#### AI-02：改善シナリオの比較支援

初期版は画面の選択肢・フォームで比較条件を指定する。自由文からの条件設定は将来候補AI-F01で扱う。比較案の生成・評価は数理最適化と検証処理が行い、AIは結果を要約する。

| 比較条件 | 公開前 | 公開後 |
| --- | --- | --- |
| 人数・スキル充足と希望充足の優先順位変更 | 比較可 | 出退勤・公開済み休憩を維持した業務配置の範囲で比較 |
| 担当業務の組み替え | 比較可 | 比較可 |
| 登録済み勤務パターンの選び直し | 必須条件を守る範囲で比較可 | 対象外 |
| 自動休憩の時刻変更 | 許容範囲内で比較可 | 変更不可。公開済み休憩を維持 |

勤務不可・勤務時間上限・連続勤務・休日数・契約条件を自動で緩和しない。固定指定を維持し、手動例外は既存の理由記録・公開ルールを維持する。

**操作フロー案：**

1. 元案のシフト版と計算条件を比較基準として保持する。
2. 管理者が比較条件と変更許可範囲を選び、変更点を確認して計算を開始する。
3. 数理最適化で代替案を計算する。
4. 必須条件・固定・公開後の出退勤と公開済み休憩の維持を検証し、指標・差分を集計する。
5. AIが比較結果を要約する。
6. 管理者が案を採用し、通常の公開前チェックを経て公開する。

**比較する指標：** 必須条件違反、業務・スキル・役割不足、不足時間枠数、必要処理能力の充足率、希望充足率、勤務変更人数、業務変更人数・時間、休憩変更人数、固定維持、出退勤維持、公開済み休憩維持、計算状態・時間。

例：「不足が1人相当減り、3人の担当業務が変更されます。出退勤時刻と固定指定は維持されています。」数値と維持条件は計算・検証結果から取得する。

比較数は元案＋代替1案とする（Q105）。AIが独断で再計算・採用・公開を連続実行する構成にはしない。

### 18.1 時点ごとの不足積算

必要能力3.0に対して、10:00〜10:30は能力4.0、10:30〜11:00は2.0なら、前半不足0、後半1.0×0.5時間で合計0.5人時間。前半の余剰で相殺しない。60分枠の先頭10分が準備なら、状態変化点で区切って10/60時間の不足を正確に積算する。役割人数も同じ区間で再計数し、能力換算人数と区別する。

### 18.2 必須条件と取消の境界

最低勤務量は上限と同様の必須条件。休暇は月下限矛盾時に承認停止（Q84）。実際の欠勤は事実記録ができても、月下限矛盾時は設定調整まで取消確定を停止（Q121）。固定解除も事前に必要。承認・確定できた取消は即時反映し、対象参加登録を自動解除する。その後の再配置は管理者が確認・公開する（第7章）。

公開後の残る勤務・休憩時刻を維持し、業務配置だけを変更する。月下限に矛盾があっても通常勤務時刻や下限を自動変更しない。履歴不足の参考案は検証済み案と区別し、公開しない。

### 18.3 実装の状態

今回の更新は仕様・計画・テスト戦略・最適化詳細の更新であり、モック・計算エンジンへQ73〜Q131を実装したものではない。設定データの具体値、技術・数値設計、人数算出方式、性能・復旧の検証は第11章・別文書で管理する。

### 22.1 詳細仕様との同期と影響

Q122により、従来の業務別「希望／充足優先」はチーム・実行単位の全体方式に統一した。業務別の役割先行／同段階は維持する。Q127により配置枠を超える準備の旧検討案を採用しない。Q131により公開済み自動休憩を固定扱いへ変更する案は採用しない。

取消後の休憩・希望、業務網羅・継続を[最適化モデル詳細仕様書](shift_management_optimization_model.md)第7・10・13章で具体化した。担当業務のない待機を認めないため、取消・予定参加解除後の残る勤務に業務未配置や継続違反が生じる場合も、条件の仮検証と必要な調整を行う設計案。確定取消の即時反映と、その後の通常の再配置案を分け、未検証の配置を検証済みと表示しない。
