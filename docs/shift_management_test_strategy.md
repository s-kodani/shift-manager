## 1. 目的と品質上の優先順位

勤務条件を守り、管理者が採用・公開できるシフトを作成することを最優先とする。一般業務やSV・リーダーの不足は、勤務条件違反と区別して表示する。最適性を証明できない案も採用できるが、計算状態と案の限界を誤って説明しない。

| 優先度 | 重点 | 合格の考え方 |
| --- | --- | --- |
| P0 | 勤務ルール、勤務不可、固定、公開後の維持条件 | 許可されていない違反がある案を採用・公開へ進めない |
| P0 | 企業・チーム・本人のデータ分離 | 画面・API・計算・入出力・AIで越権参照・更新を防ぐ |
| P0 | 公開版、休暇承認、同時更新 | 古い結果や重複処理で確定情報を壊さない |
| P1 | 不足・能力・役割・希望・余剰 | 状態変化で区切った分単位区間の独立集計と一致する |
| P1 | 計算状態、時間、案品質 | 未発見と実行不可能を区別し、規模別に有効案と待ち時間を測る |
| P1 | 管理者・スタッフの主要操作 | 登録から公開、休暇承認、再配置まで完了する |
| P1 | AI説明・比較 | 根拠ある数値を説明し、障害時は定型表示で操作を継続できる |
| P2 | 操作性・表示・運用効率 | PC・スマートフォンで確認・修正の負担を抑える |

P0〜P2はテストの優先順位であり、不具合の重大度は第12章で別に判断する。初期版は本開発後のv1.0を指し、MVPと区別する。MVPで設定画面やファイル形式を絞っても、試験対象に適用する必須条件の検証は省略しない。

## 3. ソルバーから独立した正しさの検証

### 3.1 条件チェッカー

ソルバーが返した勤務・配置・休憩を、計算に使った入力スナップショットと照合する。ソルバーの変数や「制約を満たした」という自己申告だけでは合格にしない。手動編集した案も、採用・公開時点で適用する勤務条件と照合する。

チェッカーは、勤務時間・勤務日数・連続勤務・休日・契約・勤務不可・休憩・スキル・重複配置・固定・公開済み時刻・例外の範囲を検証する。不足と目的指標も別実装で再計算する。ソルバーの制約式をコピーしただけのテストにはしない。

| 出力 | 内容 |
| --- | --- |
| 公開を阻止する違反 | ルールID、スタッフ、日時、入力値、実測値、違反量 |
| 許可された例外 | 手動の勤務不可例外と理由。再計算では固定された対象と一致するもののみ |
| 公開を妨げない不足 | 業務・役割・状態変化区間別の不足と合計 |
| 再計算した指標 | 不足、希望、余剰の値と単位 |
| 根拠の版 | 入力、設定、案、公開元のバージョン |

設定スキーマや日付型は共有できるが、ソルバーとチェッカーの制約判定を独立させる。チェッカー自身にも違反案を入力して検知能力を確認する。手計算・全列挙・別担当レビューを併用し、チェッカーも誤り得ることを前提にする。

### 3.2 小規模の正解と目的関数

数人・数日・少数業務の候補を全列挙し、実行可能案と目的値の集合を求める。複数の正解がある場合、配置の完全一致ではなく、必須条件と最良の目的値が一致することを確認する。

充足優先の「不足→希望→余剰」は、選択した不足評価方式に従い、先行段階の評価値を悪化させないことを検証する。希望を改善するために不足を増やす、余剰を減らすために希望を悪化させる、といった逆転を小規模ケースで検出する。重み付き一括評価だけで、この優先順序を満たしたと判断しない。

役割先行方式では役割不足を先に評価し、その水準を守って一般不足を評価する。同段階方式では等重みの不足評価を使う。現行案との品質比較も同じ評価順序で行う。例として、役割不足が1→0、一般不足が1→2の案は役割先行なら改善となり得るため、一般不足だけで不合格にしない。各不足値は別々に表示する。希望優先では希望未充足を先に最小化し、その値を悪化させない範囲で不足を減らす（Q85）。同段階の不足は等重みで、業務間も同等とする（Q111・Q114）。業務ごとの役割先行／同段階の合成はTD-05の残る技術設計を検証する。

先行段階の最適性が時間制限で未証明なら、その状態を表示する。後段でも保持する先行評価値を悪化させない。未証明の案を「不足が最小」と断定しない。

### 3.3 30分単位の数値例

60分枠の必要能力は、前半・後半それぞれに同じ値を適用する。以下を固定した期待値のケースにする。

| 30分枠 | 必要能力 | 稼働能力 | 不足能力 | 不足人時間 |
| --- | ---: | ---: | ---: | ---: |
| 10:00〜10:30 | 3.0 | 4.0 | 0.0 | 0.0 |
| 10:30〜11:00 | 3.0 | 2.0 | 1.0 | 0.5 |
| 合計 | — | — | — | 0.5 |

前半の余剰で後半の不足を相殺しない。能力0.5の一般スタッフが30分稼働した処理能力量は0.25人時間だが、役割比率の分母では稼働実人数1人として扱う。兼任中のSV・リーダーは分母に含めない（Q77）。処理量と時点の人数を混同しない。

## 12. 不具合重大度と工程ゲート

| 重大度 | 例 | 対応 |
| --- | --- | --- |
| S0：最重大 | 企業間漏えい、公開勤務の破損、許可されない違反の公開 | 導入・リリースを止め、原因修正と関連再検証 |

| S2：中程度 | 限定条件の不具合、迂回可能な操作問題 | 影響・回避方法・期限を記録して判断 |

未解決S0／S1を理由記録だけで許容しない。勤務不可の理由付き例外は業務仕様であり、不具合の免除ではない。問題機能を無効化して代替経路で進む場合は、範囲・検証結果・再開条件を記録する。

| --- | --- | --- | --- |
| G0：モデル採用 | A1終了 | 小規模正解、必須条件、目的順序、状態一致。101／500人のリスク把握 | 正解表、チェッカー結果、性能・選定メモ |

## 13. データ・自動化・証跡

### 13.1 データ群

小規模手計算・全列挙、既知の実行可能案、矛盾、不足、境界、2企業以上の権限、101／250／500人の合成ケース、匿名化した実チームの1か月を用意する。矛盾データは1要因ずつ追加し、原因を切り分ける。

実データ利用範囲・保存期間を企業と合意する。CIに認証情報・不要な個人情報を保存しない。再現データも最小化する。

### 13.2 性質を使う検証

生成入力に対して、同時に二重配置されない、能力・不足が負にならない、休憩が勤務外へ出ない、ID置換で条件・評価の意味が変わらない、などの不変条件を確認する。

「需要だけを増やすと最小不足は減らない」といった最適値の性質は、同一条件・小規模で最適性を証明できる問題に限定する。時間切れの案同士に機械的な単調性を要求しない。許容差は合意した数値精度に合わせる。

### 13.3 自動実行

現在の公開版CI（2026-11-15）は、継続する回帰検査と手動診断を次のように分ける。工程名A0〜A1の完了判定と、変更ごとの品質検査を区別する。

| 実行 | 対象 | 起動条件 |
| --- | --- | --- |
| `CI / worker` | 公開ソース境界、型生成・型検査、運用・API・クライアント全回帰、API・operator・backupのdry-runビルド、実Container checkerの取消境界 | PR、mainへのpush、手動 |
| `CI / optimizer` | lock整合・lint・Python全回帰、linux/amd64実イメージ、単一業務と採用済みヒントのCLI、health・実行環境・HTTP solve／独立check・保存済み候補の採否・改変拒否 | PR、mainへのpush、手動 |
| `Security checks / security` | Actions構文、秘密値履歴・作業ツリー、SAST、依存・Container・SBOM、ルールfixture | PR、mainへのpush、手動 |
| `Optimizer diagnostics / optimizer-diagnostics` | CLI全7パターン、`/benchmark`のヒント3戦略、通常の実Container probe | 手動のみ |

mainの必須チェック名は`worker`・`optimizer`・`security`を維持する。診断へ移すのは実行方式の比較であり、既存のPython回帰や`/benchmark`の入力・境界テストは通常CIで全件実行する。通常の`probe-container.mjs`は比較を省き、`--benchmarks`で追加する。実行手順・対象ブランチの指定は[README](../README.md#ciと手動診断)を参照する。

各jobの時間上限はworker・optimizer・診断が15分、securityが20分。optimizer・診断・取消境界・セキュリティの取得済みレポートは失敗時も7日間保存し、検査失敗を成功へ置き換えない。新設した手動workflowのGitHub起動確認はmain反映後に行う。ローカルでの試験成功とGitHub上の実行成功を分けて記録する。

以下は製品全体の検証計画であり、現在のCIで全項目を実行済みとするものではない。

| タイミング | 内容 |
| --- | --- |
| 変更・PRごと | 型・静的検査、単体、小規模モデル、チェッカー、重要API・権限、主要E2E |
| 定期実行 | 長い回帰、101／250／500人、複数乱数種、AI固定評価、ブラウザ |
| ルール・ソルバー変更 | 全必須条件、目的順序、精度、性能比較 |

高速検証と長い探索・負荷を分ける。長いテストを無言で省略せず、結果が必要なゲートを決める。実行時間予算は技術構成に合わせる。
